# M06 operator workflows — implementation detail

Revision 1 · 2026-10-24 · Reviewed against the approved M06 design before implementation.

The local devops CLI invokes a short-lived Order History container in non-web operator mode. It sends the operator token and request on standard input, validates the operator realm issuer and API audience, and records the verified token subject. Credentials and tokens are never command arguments or audit payloads. Customer API authorization is unchanged.

Replay reads the original retained DLQ record by its source coordinate, validates correction identity, and checks the applied inbox. It commits an immutable audit row plus durable delivery intent before publishing the corrected event to the original partition. Acknowledged publication updates a separate delivery row. A retry after publish but before receipt persistence may republish; the consumer's event identity and content hash prevent duplicate projection effects. Reusing an operation ID with changed coordinate, correction, actor or reason conflicts. An applied event cannot be rewritten. The demo corrupts the version of an existing event; correcting it demonstrates DLQ recovery without inventing an extra commerce order.

Hashes compare canonical event JSON, including recursively sorted object keys, equivalent numeric values and preserved array order. An additive canonical-hash column preserves existing raw hash evidence. Legacy records are upgraded when the exact original payload is redelivered or a retained Kafka record proves the original fingerprint. New inbox and pending events retain raw and canonical fingerprints. Consumer and replay validation reject fields outside the immutable event contract, incomplete snapshots, malformed ownership keys and fractional sequences.

Rebuild creates a separate database and consumer group, consumes retained events to two successive high-water marks, carries forward replay audits, and reconciles IDs, canonical hashes, current states, owners and money against local owner-only Orders SQL checks. A local atomic target file names the database/group used by Compose. Cutover recreates Order History with that pair; readiness failure restores the previous target. Failed candidates never replace the active target. Future rebuild implementation must prove both injected reconciliation failure and successful cutover.

Review findings resolved: avoid a new customer-facing operator API; make the DB/Kafka replay boundary explicit; persist publication intent for restart; retain immutable audit separately from mutable delivery state; preserve legacy fingerprint evidence; keep demo events tied to real synthetic Orders facts; and require candidate failure to preserve the active target. This is an implementation-owner review; independent runtime review remains a later gate.
