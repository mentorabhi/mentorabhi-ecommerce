# S1-M02 — Same services, alternate local deployment

This bounded exercise teaches deployment boundaries (R11–R13), operational
verification (R16) and reproducible local tooling (R19). It deploys only the
Catalog/Configuration bootstrap services, PostgreSQL and Keycloak. Terraform
records a desired deployment specification; it does not provision the stack.
Kubernetes is an alternative to the Compose core, not a second concurrent stack.
Allow time for image downloads separately from offline runtime execution.

## Sources and preparation

Read `design/S1-M02/bootstrap.md`. Independently built application sources live
in `services/catalog` and `services/configuration`; use the host bootstrap build
workflow to produce `supersports/catalog:s1-m02` and
`supersports/configuration:s1-m02` before this exercise. No new `manage.py`
commands are introduced here. Stop the core Compose profile using its delivered
`down` command (data is preserved). Confirm Docker Desktop is running.

Tool versions verified from official sources on 2026-10-23:

- [Helm installation](https://helm.sh/docs/intro/install/): 4.3.1, Apache-2.0.
- [kind quick start](https://kind.sigs.k8s.io/docs/user/quick-start/): v0.33.0,
  Apache-2.0. The [release notes](https://github.com/kubernetes-sigs/kind/releases/tag/v0.33.0)
  publish the Kubernetes 1.37.0 node digest used in `devops/kubernetes/kind.yaml`
  and state amd64/arm64 support.
- [Terraform installation](https://developer.hashicorp.com/terraform/install):
  1.17.0, BSL-1.1, with Darwin ARM64 download and signed checksum instructions.

Download platform-matching release binaries into ignored `devops/.local/bin`;
verify upstream checksums/signatures before use. Do not install globally. Use a
kubectl compatible with Kubernetes 1.37 per its official release instructions.
The commands below assume verified `kind`, `helm`, `kubectl`, `terraform` binaries
in that directory. Helm's upstream CI tests Linux AMD64; validate this Mac
explicitly. Application/dependency licenses and exact PostgreSQL/Keycloak
multiarch digests are recorded in the bootstrap design and chart values. Native
workloads, image compatibility, actual RSS and the 16 GB budget need measurement.

## Create the local cluster and external inputs

Run from the repository root. Use a dedicated namespace/release for this project.
The kind API server listens on 127.0.0.1; there are no node host-port mappings,
NodePorts, ingress controllers, public services or cloud providers.

```sh
export PATH="$PWD/devops/.local/bin:$PATH"
kind create cluster --name supersports --config devops/kubernetes/kind.yaml
kubectl config use-context kind-supersports
kind load docker-image --name supersports supersports/catalog:s1-m02 supersports/configuration:s1-m02
kubectl create namespace supersports
```

Prerequisite: the host bootstrap unit has generated private
`devops/.local/bootstrap.env` with the eight password keys listed in
`devops/helm/supersports/README.md`. Do not source it, print it, paste passwords
into command arguments or commit it. Keep its directory mode 0700 and file mode
0600. Kubernetes Secret data is base64, not encryption; access to the local
cluster is access to these synthetic credentials. Use only this project's
synthetic credentials and local cluster.

```sh
kubectl -n supersports create secret generic supersports-bootstrap --from-env-file=devops/.local/bootstrap.env
kubectl -n supersports create configmap supersports-postgres-init --from-file=init.sh=devops/postgres/init.sh
kubectl -n supersports create configmap supersports-realm --from-file=supersports-realm.json=devops/identity/supersports-realm.json
helm lint devops/helm/supersports \
  --set existingSecret=supersports-bootstrap \
  --set bootstrap.postgresExistingConfigMap=supersports-postgres-init \
  --set bootstrap.realmExistingConfigMap=supersports-realm
helm template supersports devops/helm/supersports --namespace supersports \
  --set existingSecret=supersports-bootstrap \
  --set bootstrap.postgresExistingConfigMap=supersports-postgres-init \
  --set bootstrap.realmExistingConfigMap=supersports-realm
helm upgrade --install supersports devops/helm/supersports --namespace supersports --create-namespace \
  --set existingSecret=supersports-bootstrap \
  --set bootstrap.postgresExistingConfigMap=supersports-postgres-init \
  --set bootstrap.realmExistingConfigMap=supersports-realm \
  --wait --timeout 10m
kubectl -n supersports get pods,services,pvc
```

All three external resource names are mandatory; unconfigured Helm lint/render
must fail. Services and references are release-scoped; bootstrap resources and
Secret must be in the release namespace. ConfigMap changes must come from the
same host-owned source files; recreate inputs deliberately between exercises.
Initialization affects only a fresh PostgreSQL volume. Existing realms are
preserved on import. Changing the Secret does not migrate existing passwords.

## Check readiness and identity from the host

Run each port-forward in its own terminal and stop with Ctrl-C:

```sh
kubectl -n supersports port-forward --address 127.0.0.1 service/supersports-identity 8180:8080
kubectl -n supersports port-forward --address 127.0.0.1 service/supersports-catalog 8081:8080
kubectl -n supersports port-forward --address 127.0.0.1 service/supersports-configuration 8082:8080
```

```sh
curl --fail http://127.0.0.1:8081/actuator/health/liveness
curl --fail http://127.0.0.1:8081/actuator/health/readiness
curl --fail http://127.0.0.1:8082/actuator/health/readiness
curl --fail http://localhost:8180/realms/supersports/.well-known/openid-configuration
curl -i http://127.0.0.1:8081/api/v1/catalog/status
curl -i http://127.0.0.1:8082/api/v1/configuration
```

Expect health UP and anonymous API 401; discovery must report issuer
`http://localhost:8180/realms/supersports`. JWT validation uses that exact issuer
and `supersports-api` audience while fetching keys through the private identity
Service. Keycloak probes use port 9000; application traffic uses 8080.
Use the host unit's documented synthetic authentication regression workflow for
customer/catalog-admin Catalog 200, platform-admin Configuration 200, wrong role
403, and wrong-audience/tampered token 401; do not log passwords or tokens. Those
checks must target these forwarded endpoints before claiming Kubernetes auth
acceptance. SQL isolation and outage/recovery likewise need actual cluster checks,
not the Docker profile's results relabeled as Kubernetes evidence.

Record actual command/tool versions, pod image IDs, outcomes, restarts, database
migration/persistence checks and measured resource usage. `kubectl top pods` needs
a metrics server which is deliberately not added here; use Docker/node process
measurement or an explicitly installed local tool and record its limitations.
Allocated limits total 2176 MiB, excluding cluster/host overhead; this is a budget,
not a measurement. Before calling the exercise verified, restart app/identity pods
and confirm settings/realm persist; inspect PVC retention separately from uninstall.

## Teardown and evidence boundary

```sh
helm uninstall supersports --namespace supersports
kubectl -n supersports get pvc
```

The StatefulSet PVC remains after Helm uninstall; reinstallation reuses stored
data. To discard this exercise completely, stop port-forwards and deliberately
run `kind delete cluster --name supersports`; this destroys that cluster's local
storage, namespace, ConfigMaps and Secret. Do not treat this as a commerce restore
procedure. Restart the Compose profile only after the alternate cluster is stopped.

U3 authoring evidence: baseline HEAD matched
`fe7b7d98322a70728f9e15a30454a9d18b37b344`. There were no existing owned deployment
files/tests. Terraform native tests were added; declarative Helm/kind manifests
use schema/render/runtime verification instead of YAML-mirroring unit tests per
the design. No red test outcome, Helm render/lint, Terraform validation/test,
cluster deployment, authenticated request, isolation test or memory measurement
is claimed by authoring this lesson. Host verification is authoritative.

Bounded authoring checks: `.venv/bin/python` parsed `values.schema.json` and
checked newline/trailing whitespace across all 13 owned files successfully.
`git diff --check` returned 0, but the new files were untracked, so the explicit
file check supplies their whitespace evidence. Helm/Terraform/kind were not on
PATH; the venv had neither PyYAML nor jsonschema. No tools/dependencies were
installed. The initial read-only heredoc check was blocked by sandbox temporary
file creation; its approved rerun passed. Shared init/realm files were absent at
inspection, so host integration must verify those ConfigMap source files before
executing the exercise.

Considered and not built: duplicate init/realm assets (precreated ConfigMaps avoid
drift); operators, ingress, cloud providers and Terraform provisioners (outside
this bounded local specification exercise). No extra management interface added.
