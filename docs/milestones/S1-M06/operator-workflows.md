# M06 operator workflows — implementation detail

Revision 2 · 2026-10-24 · Rebuild detail implemented against the approved M06 design; runtime evidence belongs in the verification record.

The local devops CLI invokes a short-lived Order History container in non-web operator mode. It sends the operator token and request on standard input, validates the operator realm issuer and API audience, and records the verified token subject. Credentials and tokens are never command arguments or audit payloads. Customer API authorization is unchanged.

Replay reads the original retained DLQ record by its source coordinate, validates correction identity, and checks the applied inbox. It commits an immutable audit row plus durable delivery intent before publishing the corrected event to the original partition. Acknowledged publication updates a separate delivery row. A retry after publish but before receipt persistence may republish; the consumer's event identity and content hash prevent duplicate projection effects. Reusing an operation ID with changed coordinate, correction, actor or reason conflicts. An applied event cannot be rewritten. The demo corrupts the version of an existing event; correcting it demonstrates DLQ recovery without inventing an extra commerce order.

Hashes compare canonical event JSON, including recursively sorted object keys, equivalent numeric values and preserved array order. An additive canonical-hash column preserves existing raw hash evidence. Legacy records are upgraded when the exact original payload is redelivered or a retained Kafka record proves the original fingerprint. New inbox and pending events retain raw and canonical fingerprints. Consumer and replay validation reject fields outside the immutable event contract, incomplete snapshots, malformed ownership keys and fractional sequences.

Rebuild creates a separate database and consumer group, consumes retained events to two successive high-water marks, carries forward replay audits and delivery intents, and reconciles IDs, canonical hashes, timeline content, current states, owners, lines and money against explicitly local owner-only Orders SQL checks. Candidate creation initially disables connections, revokes PUBLIC privileges, then enables only owner access. No application service reads another service's database.

A local atomic target file, `devops/.local/order-history-target-<project>.json`, names the database/group used by Compose. Cutover starts the candidate pair with an explicit Compose override, waits for readiness, then commits that pair to the file. Startup failure recreates the previous pair. A mismatch fails before cutover. Both candidate and previous databases remain available for diagnosis; receipts under `.local/stream-rebuilds/` record candidates, high-water marks, reconciliation, and status. A confirmed runtime reset also clears the saved target. Rebuild operations are refused against the active target, and the service requires an explicit candidate-mode flag before applying the mismatch probe.

Poison demo, replay and rebuild CLI commands share a local file lock so replay audit cannot change while being copied. Database audit copy uses owner/admin `pg_dump` and `psql` through stdin; payloads and credentials are not printed. Source snapshots before and after replay/reconciliation must match; changing workloads retry a bounded number of times and fail safely if no stable comparison window is found. Events committed after the final captured mark remain available to the new group's normal consumer. A dry run performs all candidate work and reconciliation without cutover.

The command compares historical facts only within retained outbox/Kafka data. PostgreSQL timeline timestamps have microsecond precision, so comparison permits a one-microsecond conversion difference. Kafka event and DLQ topics explicitly use unlimited time retention for the reset-controlled local learning dataset. Disk management and wider failure/load acceptance remain documented gates.

Review findings resolved: avoid a new customer-facing operator API; make the DB/Kafka replay boundary explicit; persist publication intent for restart; retain immutable audit separately from mutable delivery state; preserve legacy fingerprint evidence; keep demo events tied to real synthetic Orders facts; and require candidate failure to preserve the active target. This is an implementation-owner review; independent runtime review remains a later gate.
