# M07 implementation units and repository intake

2026-10-24 · Supplements the reviewed design with current source evidence and unit checkpoints.

## Intake findings

- `PaymentSimulator.execute` currently checks only whether an authorization/capture exists. New operation keys can repeat captures or refunds without a cumulative cap; VOID does not remove the prior authorization fact. Its operation fingerprint omits order ID. M07 must close these ledger invariants before exposing customer cancellation/returns.
- Fulfillment currently owns one `SCHEDULED` shipment row and an internal schedule/status API. It has no handoff, transit, delivered, cancellation or operator progression contract.
- Orders stores immutable line/quote/address facts and an outbox, but its worker ends at `FULFILLMENT_SCHEDULED`. A separate persisted post-purchase workflow must preserve fencing and operation identities across restarts.
- Inventory owns checkout allocations; physical return inspection/restock needs a separate return operation identity and audit rather than reusing checkout reservation transitions.
- Reviews and Support are new independent service projects. Both require customer ownership and operator/customer audience isolation, plus narrow authoritative Orders lookups.

M07 Unit 1's reviewed design and state diagram are in `payment-ledger-design.md` and `payment-ledger-flow.mmd`; Payment-owned ledger bounds are implemented and had a focused verification pass before the user requested a development-first sequence. Unit 2's reviewed design and state diagram are in `tracking-handoff-design.md` and `tracking-handoff-flow.mmd`.

## Units in dependency order

1. **Payment ledger correctness.** Serialize operations per order using its existing payment fence lock. Verify same-key order ownership as well as payload. Enforce one authorization decision and one full capture, valid void eligibility, immutable currency, and cumulative refunds at most captured funds. Keep zero-value orders valid. Derive existing balances from the service-owned ledger; do not infer money from Orders or Catalog. Add direct API integration/concurrency checks, including last refundable capacity, same-key replay/conflict and capture after void.
2. **Tracking and handoff.** Implemented, verification deferred: Fulfillment has additive revision/ETA/audit schema, strict sequential milestones, idempotent operation IDs, revision preconditions and local operator audience. Orders adds owner-checked tracking through the checkout worker identity and returns explicit UNAVAILABLE when the simulator cannot be read. UI advancement and lifecycle event mirroring are deferred to Unit 8 so the current v1 History consumer is not sent unsupported events. Scheduling, handoff/cancel claims and progression share the shipment row lock.
3. **Cancellation workflow.** Development source is now present, pending the consolidated verification pass. Customer eligibility requires a settled order and scheduled shipment; Fulfillment atomically claims the shipment row before payment refund and Inventory restock. Orders persists a fenced, idempotent workflow and emits allowlisted v2 `OrderCancelled` only in the final Orders transaction. A handoff race is rejected without refund/restock; ambiguous downstream failures enter visible MANUAL_REVIEW. UI and manual checks are drafted in `cancellation-manual-checks.md`.
4. **Partial returns and refunds.** Development source is now present, unverified. Orders verifies delivery through Fulfillment, reads a revisioned local return window, claims unit ordinals under the owned order/line lock, and snapshots per-unit merchandise/tax allocations from immutable terms using deterministic largest remainder. Shipping remains nonrefundable on partial returns. Orders serializes per-order refund attempts with stable Payment idempotency; Unit 5 inspection/restock remains separate. See `returns-refunds-design.md`, `returns-refunds-flow.mmd`, `returns-refunds-review.md`, and `returns-refunds-manual-checks.md`.
5. **Inspection and stock.** Development authored: Orders durably registers a narrow, retryable refunded-unit manifest with Inventory. Inventory stores receipt identity and complete per-unit decisions, actor/reason, revision and audit; only SELLABLE decisions create a positive stock movement. Exact operation replay is idempotent and changed payload conflicts. Added operator UI, OpenAPI scope/routes, unit, integration and Selenium test sources, and a separate manual guide. This is unverified; tests/builds are deferred until all Stage 1 development is complete. See `return-inspection-design.md`, `return-inspection-flow.mmd`, `return-inspection-review.md`, and `return-inspection-manual-checks.md`.
6. **Verified reviews and moderation.** Development authored: independent Reviews service/database, owner-scoped delivered-SKU proof through Orders, one pending review per customer/order/SKU, operator publish/reject audit, public published-only feed, customer review form, contract, unit/integration/Selenium source and manual guide. No new runtime check or build has been executed.
7. **Owned support.** Development authored: independent Support service/database, minimal linked-order proof through Orders, owner-predicated ticket reads, idempotent customer/operator messages, audited status transitions and resolution reopen, customer and operator UI, contracts, test sources and manual guide. No new runtime check or build has been executed.
8. **UI, events and final verification.** Customer tracking/cancel/return/review/support and operator shipment/inspection/moderation/support controls are authored. The v2 envelope/schema and dual-version History parser foundation are implemented; cancellation/return events are emitted from Orders, while review/support text is excluded. Compose/deployment identities and separate databases for Reviews/Support are authored. Unit/contract/integration/regression/Selenium sources and manual/database checklists are present. A tracking outbox mirror is deliberately not emitted; customer tracking remains an authoritative owner query. Whole milestone audit and consolidated verification remain follow-up work, with test execution deferred until all Stage 1 development is complete.

## Review disposition and policy defaults

Implementation-owner review resolved refund capacity, authorization after void, cross-order idempotency, shipment handoff races, return quantity and refund allocation, independent inspection/restock, token forwarding/retention, and event-version compatibility before coding these units. These are local simulated-store policy defaults, not real provider or legal behavior. Policy settings must be versioned and shown in eligibility responses; accepted requests retain their policy/allocation snapshot.

Use the existing pinned Java/Spring/PostgreSQL stack unless a unit introduces a dependency that requires a fresh stable-version/ARM64/license check. Extend public contracts under `contracts/`; all infrastructure and cross-service test orchestration stay under `devops/`. Units may be checkpointed separately on `stage1`; the M07 milestone is complete only after all required journeys and invariants are verified.
